Project 20: Push Test Data Pipeline + Dashboard

Tujuan project: membangun pipeline yang membaca file CSV mesin push test secara otomatis, membersihkan angkanya, dan menyimpannya di database, sehingga Max, Min, rata-rata, dan Cpk kekuatan rekat per model dan kondisi proses bisa dipantau di dashboard tanpa macro VBA dan copy-paste manual.

Kategori:Rancangan projectPerakitan sepeda motorData simulasiPython + SQL pipeline

Project Introduction

Bayangkan sekolah yang memakai mesin pemindai lembar jawaban. Setiap kelas menghasilkan satu file nilai. Guru lalu menyalin file-file itu satu per satu ke buku nilai dengan bantuan macro, dan kadang nilai 8.245,6 terbaca 8,2456 karena tanda titik dan koma tertukar. Rapor jadi salah, dan tidak ada yang sadar sampai orang tua protes.

Sekolah butuh cara agar setiap file nilai baru langsung terbaca dengan benar, tersimpan di satu tempat, dan rapor bisa dilihat kapan saja tanpa menyalin manual.

Project ini membangun pipeline data: file CSV dari mesin push test dibaca otomatis, divalidasi, disimpan di database, lalu ditampilkan di dashboard per model dan kondisi proses. Datanya adalah data simulasi karena data pabrik bersifat rahasia. Kata bergaris bawah putus-putus kuning bisa diklik untuk melihat artinya.

Gambaran alur kerja di lini perakitan lampu depan sepeda motor

Lini produksi bisa dibayangkan sebagai tiga jalur yang berjalan bersamaan. Dua jalur pertama sudah ada di pabrik. Jalur ketiga adalah yang dibangun di project ini.

  1. Jalur produksi. Rumah lampu dicetak, lem diaplikasikan, lensa ditempel, lalu lem dikeringkan di oven sebelum lampu diperiksa dan dikirim ke lini perakitan motor.
  2. Sampel diambil. Beberapa unit per shift diambil sebelum dan sesudah oven untuk diuji kekuatan rekatnya, seperti lembar jawaban yang dipindai.
  3. Jalur push test. Mesin menekan lensa sampai lepas dan mencatat gayanya dalam satu file CSV per sesi. Saat ini file disalin ke Excel dengan macro VBA dan copy-paste, rawan salah baca angka dan file terlewat.
  4. Jalur data. File baru dibaca otomatis, divalidasi, disimpan di database, lalu ditampilkan di dashboard. Engineer cukup membuka link untuk melihat Cpk terbaru.

1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Di banyak pabrik, mesin uji menyimpan hasilnya sebagai file CSV per sesi. Data lalu dipindahkan ke Excel memakai macro VBA dengan alamat folder yang ditulis langsung di kode, ditambah copy-paste manual. Akibatnya:

  • Setiap file butuh beberapa menit untuk dipindahkan, dan pekerjaan menumpuk saat volume uji tinggi.
  • Angka dengan titik ribuan dan koma desimal bisa salah dibaca (8.245,6 g menjadi 8,2 g), sehingga rata-rata dan Cpk terlihat jauh lebih buruk dari kenyataan.
  • Macro berhenti jika nama folder atau format kolom mesin berubah, dan file bisa terlewat atau masuk dua kali tanpa ketahuan.
  • Cpk baru dihitung saat laporan dibuat, sehingga pergeseran proses terlambat diketahui.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan pekerjaan sehari-hari. Mengolah data mesin uji dan mengganti macro VBA adalah masalah nyata yang pernah ditangani, sehingga bisa diceritakan dengan detail saat wawancara.
  • Menunjukkan skill data engineering ringan untuk Data Analyst. Parsing file berantakan, validasi, skema database, SQL, dan dashboard yang ter-update otomatis.
  • Tingkat kesulitan menengah. Analisisnya deskriptif dan Cpk, tetapi pipeline harus tahan terhadap file rusak dan duplikat.
  • Menjadi sumber data project lain. Database hasil pipeline bisa dipakai Project 12 (Process Comparison Analysis) dan Project 15 (SPC Control Chart & Capability Dashboard with Automated Alerts), yang juga memakai data push test.

4. DatasetData simulasi buatan sendiri yang meniru file CSV mesin push test

Kenapa data simulasi? Data pabrik bersifat rahasia. Program Python membuat ribuan file CSV yang meniru keluaran mesin push test: header mesin, pemisah titik koma, titik ribuan dan koma desimal, serta beberapa file rusak. Karena kita tahu apa yang ditanam, kita bisa memeriksa apakah pipeline menangkapnya.

Ukuran: 2 model (A dan B), 2 kondisi (sebelum dan sesudah oven), 2 mesin uji, 2 shift, sekitar 75 hari kerja. Perkiraan ±1.200 file CSV dengan 5–20 hasil ukur per file, atau ±15.000 baris hasil ukur. Jumlah pastinya baru diketahui setelah data dibuat.

Sumber data: data simulasi buatan sendiri, dibuat oleh skrip scripts/generate_csv.py di repositori project (Versi: v1, rancangan; Tanggal dibuat: saat Tahap B dikerjakan). Tidak memakai dataset publik atau data perusahaan.

Fakta yang sengaja ditanam (ground truth)

1. Satu kombinasi (usulan: Model B sebelum oven) dibuat bervariasi besar sehingga Cpk di bawah 1,33.

2. Rata-rata satu mesin uji bergeser turun ±800 g selama ±1 minggu setelah kalibrasi yang salah.

3. Sekitar 3% file memakai titik ribuan dan koma desimal, format yang membuat macro lama salah baca.

4. File bermasalah: header berbeda, kolom hilang, file kosong, dan file yang sama tersalin dua kali.

5. Sekitar 2–3% nilai tidak wajar (0, negatif, atau di atas kapasitas mesin) disisipkan.

Empat tabel yang akan dibuat

Data disimpan dalam beberapa tabel yang saling terhubung lewat kolom yang sama (misalnya run_id). Satu file CSV menjadi satu baris di test_run dan beberapa baris di measurement.

5. ToolsAlat yang dipakai dan alasannya

Python (pandas)

Parser file CSV: mengenali pemisah kolom, ribuan, dan desimal, membaca header mesin, memvalidasi kolom, lalu memindahkan file gagal ke karantina.

Menggantikan macro VBA. Alamat folder disimpan di file konfigurasi, tidak ditulis langsung di kode.

DuckDB + SQL

Database untuk test_run, measurement, spec, dan ingest_log. Max, Min, rata-rata, dan Cpk dihitung lewat view SQL.

Gratis dan cukup satu file. Daftar portofolio menulis SQLite/PostgreSQL; DuckDB dipilih agar konsisten dengan project lain.

Streamlit + Plotly

Dashboard per model, kondisi, mesin, dan shift: tren rata-rata, Cpk, histogram terhadap spesifikasi, dan status file terakhir.

Bisa dipublikasikan gratis lewat link. Power BI butuh akun work/school untuk publish.

pytest

Tes otomatis untuk parser: file normal, titik ribuan dan koma desimal, header berbeda, file kosong, file duplikat.

Membuktikan pipeline tidak rusak saat kode diubah.

Excel

Cek silang: membandingkan hasil pipeline dengan workbook lama pada sampel sesi uji (Q3).

Format laporan lama tetap bisa diverifikasi rekan kerja.

GitHub + Markdown

Menyimpan kode, contoh file CSV, dan README. GitHub Actions bisa menjalankan tes setiap ada perubahan.

Standar industri untuk portofolio dan riwayat perubahan kode.

9. Assumptions & LimitationsKomponen tambahanKeputusan yang sudah diambil dan hal yang perlu diwaspadai

Jenis data: simulasi meniru file mesin Sudah Anda setujui

Semua file CSV dibuat program dengan format yang meniru keluaran mesin push test. Hasil akhir membuktikan pipeline dan metodenya bekerja, bukan menggambarkan kondisi pabrik sebenarnya.

Konteks: perekatan lensa lampu depan sepeda motor Sudah Anda setujui

Halaman publik memakai push test perekatan lensa lampu depan sepeda motor, Model A dan B, sama dengan Project 15. Struktur masalahnya (file CSV mesin, macro VBA, salah baca angka, Cpk per model dan kondisi) tetap sama.

Tools: DuckDB + Streamlit Sudah Anda setujui

Konsisten dengan project lain. Daftar portofolio menulis SQLite/PostgreSQL dan Streamlit/Power BI; kolom Tools di daftar sebaiknya diperbarui.

Ruang lingkup Usulan awal

2 model, 2 kondisi, 2 jenis uji, 2 mesin, 2 shift, ±3 bulan. Pipeline dijalankan terjadwal (misalnya setiap jam), bukan real-time. Dampak dihitung dalam menit kerja, belum dalam rupiah.

Hal yang perlu diwaspadai Usulan awal

Cpk butuh data yang cukup. Cpk dari kurang dari ±30 hasil ukur tidak stabil. Dashboard menampilkan jumlah data di samping setiap Cpk.

Spesifikasi lebar. Rentang 1.500–19.000 g sangat lebar, sehingga Cpk lebih ditentukan oleh batas bawah. Dashboard menampilkan jarak ke LSL secara terpisah.

Format mesin bisa berubah. Pipeline hanya mengenali format yang terdaftar. Format baru masuk karantina sampai aturannya ditambahkan.

Pola belum tentu penyebab. Pergeseran setelah kalibrasi baru dugaan, perlu dicek di lapangan.

Q6
Apakah hasil berbeda antar shift atau antar mesin uji?
Pendukung · Dengan catatan

Mesin berbeda: PT-02 lebih rendah 69 g dari PT-01 pada rata-rata sesi (Mann-Whitney p 0,038, p Holm 0,076), terutama karena pergeseran PT-02 (Q7). Shift berbeda kecil: Shift 2 lebih tinggi 0 g (p 0,926, p Holm 0,926); signifikan secara statistik tetapi selisihnya kecil terhadap sebaran. Mesin dan shift tidak dipisah dari waktu, jadi perancu belum dikendalikan.

Q7
Bagaimana tren rata-rata kekuatan rekat dan Cpk per minggu, dan adakah pergeseran?
Utama · Terjawab

Rata-rata mingguan gabungan stabil sekitar 7.676 g dan Cpk mingguan antara 1,36 dan 1,70 (14 minggu). Penurunan ada di mesin PT-02: jendela 2026-05-23 sampai 2026-05-29, rata-rata turun 808 g (10,6%), p permutasi < 0,001. PT-01 tidak punya jendela penurunan (p 0,149). Jendela 7 hari adalah asumsi (rancangan: sekitar 1 minggu); jendela 5 dan 10 hari memberi selisih -804 dan -567 g (Tabel 2.4f).

Q8
Apakah pergeseran terjadi setelah kalibrasi mesin atau penggantian lot lem?
Pendukung · Dengan catatan

Penurunan PT-02 terjadi 2026-05-23 sampai 2026-05-29 dan tidak muncul di PT-01. Data tidak memuat catatan kalibrasi atau lot lem, sehingga penyebabnya tidak dapat dipastikan dari data; pada simulasi pergeseran ditanam sebagai kalibrasi mesin. Pergeseran belum tentu sebab kalibrasi dan perlu dicek di lapangan.

Q9
Berapa menit kerja manual per file yang digantikan pipeline?
Utama · Dengan catatan

Asumsi dasar 5 menit manual per file (salin dengan macro dan copy-paste), dibanding pipeline otomatis. Untuk 1.440 file pada periode data, penghematan 120,0 jam. Menit per file tidak diukur; sensitivitas 3 dan 10 menit di Tabel 2.4a.

Q10
Berapa jam kerja per tahun yang bisa dihemat?
Tambahan · Dengan catatan

Sekitar 481 jam per tahun (estimated): 5.776 file per tahun x 5 menit / 60. Sensitivitas: 289 jam pada 3 menit dan 963 jam pada 10 menit. Volume tahunan diekstrapolasi dari periode data (asumsi).

7. KesimpulanHasil analisis, Impact, success criteria, rekomendasi, saran perbaikan, dan batasan

7.1 Hasil analisis

Pertanyaan utama: bagaimana mengganti macro VBA dan copy-paste manual agar data CSV mesin push test otomatis masuk database, terbaca dengan benar, dan siap dianalisis per model dan kondisi proses?

Pipeline memuat 1.440 dari 1.500 file unik (96,0%), mengarantina 60 file rusak dengan alasan, dan tidak menambah baris saat dijalankan ulang. Macro lama (tiruan) salah membaca 424 nilai (3,1%) sehingga Cpk terlihat 0,40 sampai 1,83 lebih rendah. Cpk Model B before oven 1,04 di bawah 1,33 (kombinasi lain di atas) dengan 4 hasil ukur di luar spesifikasi. Rata-rata mesin PT-02 turun 808 g pada 2026-05-23 sampai 2026-05-29 dan terdeteksi di tanggal yang ditanam. Semua 109 kategori file rusak yang ditanam tertangkap, tanpa file normal salah karantina.

7.2 Impact

Estimasi (estimated): sekitar 481 jam kerja manual per tahun (5 menit per file x 5.776 file per tahun), dengan rentang 289 sampai 963 jam untuk 3 sampai 10 menit per file. Menit per file adalah asumsi, bukan pengukuran.

Nilai praktis: angka tidak lagi salah baca dan file rusak tidak masuk diam-diam. Nilai analitis: Cpk dan tren per model, kondisi, dan mesin dari satu sumber SQL. Nilai portofolio: pipeline dengan karantina, idempoten, dan uji ground truth. Belum terukur: dampak nyata di lini dan dalam rupiah.

7.4 Rekomendasi

  • Jalankan pipeline terjadwal dan tinjau folder karantina setiap hari; format mesin baru ditambahkan sebagai aturan sebelum file dimuat ulang.
  • Selidiki kalibrasi mesin PT-02: rata-rata turun 808 g pada 2026-05-23 sampai 2026-05-29.
  • Turunkan variasi Model B before oven (Cpk di bawah 1,33) dan pantau jarak rata-rata ke LSL (dalam simpangan baku) selain Cpk.
  • Hentikan macro lama setelah pipeline diverifikasi pada data nyata.

7.5 Saran perbaikan

  • Deploy dashboard dan uji ke pembaca awam (kriteria 1 menit).
  • Uji pipeline pada file mesin nyata untuk memeriksa format angka dan jenis kerusakan yang tidak ada di simulasi.
  • Ukur menit manual per file di lapangan untuk menggantikan asumsi.
  • Tambahkan catatan kalibrasi dan lot lem ke data agar penyebab pergeseran bisa diuji.

7.6 Batasan

  • Data adalah simulasi; angka menggambarkan simulasi, bukan lini produksi. Semua 109 kategori file rusak yang ditanam terdeteksi, tetapi hanya untuk kategori yang ditanam generator.
  • Macro lama ditiru dari deskripsi rancangan; workbook asli tidak tersedia, sehingga rekonsiliasi (Q2, Q3) bergantung pada tiruan itu.
  • Asumsi buatan sendiri: aturan file terpotong, kapasitas mesin, aturan baca angka, Cpk per kelompok gabungan, 5 menit per file, volume tahunan, uji shift dan mesin pada rata-rata sesi, serta spesifikasi dan nilai dasar shear test.
  • Kelima fakta data rancangan ditanam dan terdeteksi. Aliran shear test (300 file) ditambahkan dengan nilai dasar dan spesifikasi asumsi, tanpa file rusak dan tanpa pergeseran mesin; analisis Cpk, tren, dan dashboard hanya untuk push test, shear hanya punya tabel KPI dan cek silang. Generator, jenis kerusakan, dan jendela penurunan 7 hari ditulis oleh orang yang sama dengan pipeline, jadi uji pemulihan optimistis.
  • Perbedaan shift kecil tetapi signifikan (p Holm 0,926); mesin dan shift tidak dipisah dari waktu. Penyebab pergeseran PT-02 tidak bisa dipastikan dari data.
  • Dashboard belum di-deploy; kriteria pembaca awam belum diuji; slide dan file contoh di data/samples tidak dibuat; branch belum di-merge ke main.
  • Rumus Excel dihitung ulang LibreOffice, bukan Excel. Lisensi data tidak berlaku (data karangan).
